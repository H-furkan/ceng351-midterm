Database basics

What a database is and why we don't just use files. This is background; expect at most a short question on it.

Database and DBMS

A database is a large, organised collection of data, for example everything a university stores about students, courses and grades. A DBMS (database management system) is the software that stores it and lets you use it: MySQL, PostgreSQL, SQLite and Oracle are DBMSs.

Why not just files?

You could keep data in plain files and write programs to read them. That gets painful quickly. A DBMS gives you:

  • Querying: ask questions in a language like SQL instead of writing a program for every question.
  • Integrity: rules such as "every student ID is unique" are enforced automatically.
  • Concurrency: many users can read and change the data at the same time safely.
  • Crash recovery: after a power cut the data is still consistent.
  • Data independence: you can change how data is stored on disk without rewriting programs.
  • Efficiency: data that doesn't fit in memory is stored and searched efficiently on disk. That's the "file structures" half of this course, after the midterm.

Data model, schema, instance

  • A data model is the way you describe data. This course uses the relational model (data is tables) and the ER model (a drawing used to design those tables).
  • A schema is the description: table names and columns. It rarely changes.
  • An instance is the actual data at one moment: the rows. It changes all the time.
What is the difference between a schema and an instance?
The schema is the structure (table names, column names and types), like Sailors(sid, sname, rating, age). The instance is the set of rows stored right now. Adding a sailor changes the instance, not the schema.
Name three things a DBMS gives you that plain files don't.
Any three of: a query language, integrity constraints, safe concurrent access, crash recovery, data independence, efficient access to large data.

The relational model

Tables, keys and foreign keys. Sample Q1 (20 points) is entirely about this lesson.

Words you need

TermPlain meaning
RelationA table
TupleA row
Attribute (field)A column
DomainThe type of a column, such as INTEGER or CHAR(20)
Degree (arity)Number of columns
CardinalityNumber of rows

A schema is written like Students(sid: string, name: string, login: string, age: integer, gpa: real). In theory a relation is a set of rows, so all rows are different and their order doesn't matter.

Creating tables

CREATE TABLE Students (
  sid    CHAR(20),
  name   CHAR(20) NOT NULL,
  login  CHAR(10),
  age    INTEGER,
  gpa    REAL,
  PRIMARY KEY (sid),
  UNIQUE (login) );

INSERT INTO Students (sid, name, login, age, gpa)
VALUES ('53688', 'Smith', 'smith@ee', 18, 3.2);

DELETE FROM Students S WHERE S.name = 'Smith';

Keys

  • A superkey is any set of columns where no two rows can have the same values.
  • A candidate key is a minimal superkey: remove any column and it stops being unique. {sid} is a candidate key; {sid, name} is a superkey but not a candidate key.
  • The primary key is the one candidate key you choose. Declare the other candidate keys with UNIQUE.
PRIMARY KEYUNIQUE
How many per tableExactly oneAny number
Can contain NULLNeverYes, even several rows with NULL
Exam trap. Keys say something about the real world, so choose them carefully. In Enrolled(sid, cid, grade), PRIMARY KEY (sid, cid) means a student gets one grade per course. PRIMARY KEY (sid), UNIQUE (cid, grade) would mean a student takes only one course, and no two students in a course get the same grade.

NULL

NULL means the value is unknown or doesn't apply. A column declared NOT NULL rejects it.

Foreign keys

A foreign key is a column (or columns) in one table whose value must appear as the primary key of another table. It works like a pointer. In Enrolled, sid references Students: you can't enrol a student who doesn't exist. This rule is called referential integrity.

CREATE TABLE Enrolled (
  sid    CHAR(20),
  cid    CHAR(20),
  grade  CHAR(2),
  PRIMARY KEY (sid, cid),
  FOREIGN KEY (sid) REFERENCES Students(sid)
      ON DELETE CASCADE
      ON UPDATE CASCADE );
  • We call Enrolled the child (it holds the foreign key) and Students the parent (it is referenced).
  • A foreign key may be NULL, unless it is also part of the child's primary key.
  • A foreign key can reference its own table, like Employee.Supervisor referencing Employee.SSN.
  • Column names may differ (FOREIGN KEY (student_id) REFERENCES Students(sid)), but the types must match.

What happens when a foreign key would break

Only two kinds of change can break a foreign key.

1. Inserting or updating a child row so it points to a parent that doesn't exist: always rejected.

2. Deleting or updating a parent row that children still point to. The rule you wrote decides:

RuleWhat happens to the child rows
NO ACTION defaultNothing; the delete or update is rejected
CASCADEDelete: child rows are deleted too. Update: child foreign keys change to the new value.
SET NULLChild foreign keys become NULL
SET DEFAULTChild foreign keys become the column's DEFAULT value, which must exist in the parent

ON DELETE and ON UPDATE are separate rules. If one is missing, it is NO ACTION.

Exam trap. Inserting into the parent or deleting from the child never breaks a foreign key. Don't look for problems there.

How to answer a trace question

For each statement, in order, check:

  1. Primary key: does the new or changed key already exist? Is it NULL? Then reject.
  2. NOT NULL: is a NOT NULL column getting NULL? Then reject.
  3. Foreign keys of this row: does every non-NULL foreign key point to an existing parent row? If not, reject.
  4. Rows pointing at this row (for DELETE or UPDATE of a key): look in every table, including this one, for references. If any reference has NO ACTION, reject the whole statement. Otherwise apply CASCADE / SET NULL / SET DEFAULT.
  5. Write both tables after the statement. A rejected statement changes nothing.

The full sample Q1 is solved step by step in Sample midterm, solved.

Students has a row with sid 5. Enrolled has FOREIGN KEY (sid) REFERENCES Students ON DELETE SET NULL and PRIMARY KEY (sid, cid). What happens on DELETE FROM Students WHERE sid = 5 if student 5 is enrolled somewhere?
It is rejected. SET NULL would put NULL into sid, but sid is part of Enrolled's primary key, which can never be NULL. In practice you'd use CASCADE here.
What is the default when a FOREIGN KEY has no ON DELETE clause?
NO ACTION: deleting a parent row that is still referenced is rejected.
Why can a table have several UNIQUE constraints but only one PRIMARY KEY?
Every candidate key is unique, so you can declare as many as exist with UNIQUE. The primary key is the single one you pick as the main identifier; other tables' foreign keys normally reference it.

The ER model

A drawing that describes the data before you create any tables. Sample Q2a (part of 30 points) asks you to draw one from a description.

Where it fits

Designing a database goes: understand the requirements, draw an ER diagram (conceptual design), then turn the diagram into tables (logical design, next lesson).

The building blocks

  • An entity is a thing, like one employee. An entity set is all things of that kind, drawn as a rectangle.
  • An attribute is a property, drawn as an oval. The key attribute is underlined.
  • A relationship connects entities, like "Ali works in Sales". A relationship set is drawn as a diamond. It can have its own attributes, like since.
  • A relationship is identified by the keys of the entities it connects. So the same pair (Ali, Sales) can appear in Works_In only once.

Constraints: the arrow and the bold line

These two marks carry most of the points. Read them from the side of the entity they touch.

Line from entity to diamondMeaning for each entity of that setWords in the question
Thin lineAny number of relationships, including zero"may", "several", "many"
Arrow (key constraint)At most one"at most one", "only one", "a single"
Bold line (total participation)At least one"must", "every", "at least one"
Bold arrowExactly one"exactly one", "each X has one Y"

So in "each department has at most one manager", the arrow goes from Departments to Manages.

Relationship types by arrows: one-to-one (arrows on both sides), one-to-many (arrow on one side), many-to-many (no arrows).

Weak entities

A weak entity can't be identified by its own attributes. A dependent is identified by its name plus the employee it belongs to (two employees can both have a child named Ayşe).

  • Bold rectangle for the weak entity, bold diamond for its identifying relationship.
  • Its own identifying attribute is the partial key, underlined with a dashed line.
  • The weak entity has a bold arrow to the owner: each dependent has exactly one owner.
  • Delete the owner and its weak entities go too.

Trigger in the question: "unique only within a team", "different teams may have the same jersey number".

ISA hierarchies (subclasses)

Use ISA ("is a") when some entities have extra attributes: Hourly_Emps are Employees with hourly_wage. Subclasses inherit all attributes, including the key, and can take part in their own relationships.

  • Overlap constraint: can one entity be in two subclasses at once? (Can Joe be hourly and contract?)
  • Covering constraint: must every entity be in some subclass? (Is every employee hourly or contract?)

Trigger in the question: "there are two kinds of X", "if X is a ..., also record ...".

Aggregation

Normally a relationship connects entities. Aggregation lets a relationship connect to another relationship. You draw a dashed box around the inner relationship and treat it like an entity.

Use it when the question says something about a relationship itself: "a sponsorship is monitored by an employee", "the support of a team's training by a coach is funded by a sponsor".

Other things you'll meet

  • Roles: one entity set can appear twice in a relationship. Reports_To connects Employees to Employees, with role labels supervisor and subordinate on the two lines.
  • Ternary relationships connect three entity sets, like Enroll(student, course, semester). Use one only if the fact truly needs all three at once; otherwise two binary relationships are cleaner.
  • Entity or attribute? Make it an entity if it has its own attributes, or if one thing can have several of it (several addresses, several periods). An attribute holds one value.
  • A relationship can't repeat the same set of entities. If an employee can work in a department in several periods, model the period as its own entity (Duration with from and to) and connect it to the relationship.

How to draw an ER diagram from a description

  1. Underline every noun that has its own attributes: those are entity sets. Mark the word "unique" next to each: that's the key.
  2. Find "kinds of" / "if it is a ..." sentences: those become ISA.
  3. Find verbs connecting two entities: those are relationships. Values that describe the connection (date, role, amount) are attributes of the diamond.
  4. For each line, decide thin / arrow / bold / bold arrow using "at most", "at least", "must", "exactly".
  5. "Unique only within ..." → weak entity. A fact about a relationship → aggregation.
  6. Write any constraint you can't draw as a short note under the diagram. Graders like that.
“A team can attend at most one league, while a league must have at least one team.” Draw the lines.
Teams —→ Attends (arrow from Teams: at most one league). Leagues ══ Attends (bold line from Leagues: at least one team).
“Jersey numbers are unique within a team, but different teams may use the same number.” What do you draw?
A weak entity JerseyNumbers (bold box) with partial key jersey_no (dashed underline), identified through a bold diamond by its owner Teams, with a bold arrow from JerseyNumbers.
“Each professor teaches exactly one course, and every course is taught by some professor.”
Professors ══▶ Teaches (bold arrow: exactly one course) and Courses ══ Teaches (bold line: at least one professor).

From ER diagram to tables

A fixed set of rules turns any ER diagram into CREATE TABLE statements. Sample Q2b asks for exactly this.

1. Entity set → table

Each attribute becomes a column; the key becomes the primary key.

CREATE TABLE Employees (
  ssn   CHAR(11),
  name  CHAR(20),
  lot   INTEGER,
  PRIMARY KEY (ssn) );

2. Many-to-many relationship → its own table

Columns: the key of each connected entity plus the relationship's own attributes. Primary key: all the entity keys together. Each entity key is a foreign key.

CREATE TABLE Works_In (
  ssn    CHAR(11),
  did    INTEGER,
  since  DATE,
  PRIMARY KEY (ssn, did),
  FOREIGN KEY (ssn) REFERENCES Employees,
  FOREIGN KEY (did) REFERENCES Departments );

3. Arrow (key constraint) → merge into the arrow side

Each department has at most one manager, so the manager can live in the Departments table. This is the preferred way.

CREATE TABLE Dept_Mgr (
  did     INTEGER,
  dname   CHAR(20),
  budget  REAL,
  ssn     CHAR(11),          -- the manager; NULL if none
  since   DATE,
  PRIMARY KEY (did),
  FOREIGN KEY (ssn) REFERENCES Employees );

The alternative is a separate Manages(ssn, did, since) table with primary key did only, because did appears at most once. Either is accepted, but merging uses fewer tables, and the sample answer keys ask for "as few tables as possible".

4. Bold arrow (exactly one) → merge and add NOT NULL

ssn  CHAR(11) NOT NULL,   -- every department must have a manager
  FOREIGN KEY (ssn) REFERENCES Employees ON DELETE NO ACTION

A bold line without an arrow (at least one, possibly many) can't be enforced with plain CREATE TABLE. Just mention it in a note.

5. Weak entity → one table with the owner

Merge the weak entity and its identifying relationship into one table. Primary key: owner's key + partial key. Delete the dependents when the owner goes.

CREATE TABLE Dep_Policy (
  pname  CHAR(20),
  age    INTEGER,
  cost   REAL,
  ssn    CHAR(11),
  PRIMARY KEY (pname, ssn),
  FOREIGN KEY (ssn) REFERENCES Employees ON DELETE CASCADE );

6. ISA → two options

Option A (works always): one table for the superclass, one per subclass. Each subclass table holds the key and its own extra attributes. Its key is also a foreign key to the superclass, with ON DELETE CASCADE.

CREATE TABLE Hourly_Emps (
  ssn           CHAR(11),
  hourly_wages  REAL,
  hours_worked  INTEGER,
  PRIMARY KEY (ssn),
  FOREIGN KEY (ssn) REFERENCES Employees ON DELETE CASCADE );

Option B: no superclass table; each subclass table repeats all inherited attributes. Only possible if the hierarchy is covering (otherwise employees in no subclass have nowhere to go). With overlap, shared attributes get stored twice.

7. Aggregation → reference the inner relationship's key

CREATE TABLE Monitors (
  ssn    CHAR(11),
  did    INTEGER,
  pid    INTEGER,
  until  DATE,
  PRIMARY KEY (did, pid, ssn),
  FOREIGN KEY (ssn) REFERENCES Employees,
  FOREIGN KEY (did, pid) REFERENCES Sponsors );

8. Ternary relationship → one table with three keys

Same as many-to-many: Enroll(sid, cid, semID, grade) with primary key (sid, cid, semID) and three foreign keys.

Departments —→ Manages — Employees, with the arrow from Departments. Which table gets the manager's ssn if you merge?
Departments (the arrow side). Each department has at most one manager, so one column per department is enough. Employees can manage many departments, so a column there wouldn't fit.
Why does a weak entity table usually say ON DELETE CASCADE?
A weak entity can't exist without its owner; its key includes the owner's key. When the owner is deleted, the weak entities must disappear too.
When can you skip the superclass table in an ISA hierarchy?
Only when it's covering: every superclass entity belongs to at least one subclass. Ideally there's also no overlap, otherwise shared attributes are stored twice.

Union ∪, intersection ∩, difference −

Normal set operations. Both inputs must be union-compatible: same number of columns with matching types.

  • R ∪ S: rows in R or S.
  • R ∩ S: rows in both.
  • R − S: rows in R but not in S. This is how you say "not".

Cross product ×

R × S pairs every row of R with every row of S. Sailors × Reserves has 10 × 10 = 100 rows and all columns of both. Clashing column names (both have sid) need renaming.

Renaming ρ

ρ(Temp, E) names the result of E as Temp, so you can use it later. ρ(C(1→sid1, 5→sid2), S × R) renames columns 1 and 5. Use it to break long answers into steps.

Joins ⋈

A join is a cross product followed by a selection.

  • Condition join: R ⋈c S = σc(R × S)
  • Equi-join: the condition is only equalities, and one copy of each equal column is kept.
  • Natural join R ⋈ S: equi-join on all columns with the same name. Sailors ⋈ Reserves joins on sid.

SQL 1: basic queries

SELECT–FROM–WHERE, and set operations. All results come from the Example tables.

The basic query

SELECT  [DISTINCT] columns
FROM    tables
WHERE   condition

SQL works with multisets: unlike relational algebra, it keeps duplicates unless you write DISTINCT.

How SQL evaluates it

When unsure what a query returns, compute it in this order. Real databases are smarter, but they give the same answer.

  1. FROM: cross product of all the tables.
  2. WHERE: drop the rows where the condition isn't true.
  3. SELECT: keep the listed columns.
  4. DISTINCT: if present, remove duplicate rows.
SELECT S.sname
FROM   Sailors S, Reserves R
WHERE  S.sid = R.sid AND R.bid = 103;

Queries inside queries, the “all” query in SQL, and COUNT / SUM / AVG / MAX / MIN.

EXISTS and correlated subqueries

EXISTS (subquery) is true if the subquery returns at least one row. A correlated subquery uses a variable from the outer query (S.sid below), so it's re-evaluated for each outer row.

SELECT S.sname
FROM   Sailors S
WHERE  EXISTS (SELECT *
               FROM   Reserves R
               WHERE  R.bid = 103 AND R.sid = S.sid);
Result
sname
dustin
lubber
horatio

Read it as: for each sailor S, is there a reservation of boat 103 by S?

ANY and ALL

x op ANY (subquery) is true if the comparison holds for at least one value; x op ALL (subquery) if it holds for every value. IN is the same as = ANY, and NOT IN the same as <> ALL.

SELECT S.sid, S.sname, S.rating
FROM   Sailors S
WHERE  S.rating >= ALL (SELECT S2.rating
                        FROM   Sailors S2);
Result

58rusty10
71zorba10

Sailors with the highest rating. With > ALL the result would be empty, because a rating is never greater than itself.

SQL 3: GROUP BY, NULL, outer joins, changing data

GROUP BY and HAVING were excluded from ICA2, so they are a likely target for the midterm. Sample Q4 needs them.

GROUP BY: one answer per group

Aggregates so far gave one value for the whole table. GROUP BY splits the rows into groups with equal values and gives one result row per group.

SELECT S.rating, COUNT(*) AS how_many, MIN(S.age) AS youngest
FROM   Sailors S
GROUP BY S.rating;
Result

HAVING: keep only some groups

WHERE filters rows before grouping; HAVING filters groups after grouping, so it can use aggregates.

SELECT   [DISTINCT] columns
FROM     tables
WHERE    row condition
GROUP BY grouping columns
HAVING   group condition
ORDER BY columns

Evaluation order

  1. FROM: cross product.
  2. WHERE: drop rows.
  3. GROUP BY: form groups.
  4. HAVING: drop groups.
  5. SELECT: one output row per remaining group.
  6. ORDER BY: sort.

Age of the youngest adult sailor for each rating with at least 2 such sailors

SELECT   S.rating, MIN(S.age) AS minage
FROM     Sailors S
WHERE    S.age >= 18
GROUP BY S.rating
HAVING   COUNT(*) >= 2;

Exam trap. Every column in SELECT that isn't inside an aggregate must appear in GROUP BY. SELECT S.sname, COUNT(*) … GROUP BY S.rating is illegal: one rating group has several names. The same rule holds for columns in HAVING.

Comparing with NULL gives a third truth value, unknown. rating > 8 is unknown when rating is NULL.

  • WHERE keeps only rows where the condition is true. Unknown rows are dropped.
  • Test for NULL with IS NULL / IS NOT NULL. rating = NULL is never true.
  • COUNT(*) counts every row; all other aggregates ignore NULLs. COUNT(rating) skips NULL ratings, and AVG(rating) averages only the known ones.

Outer joins

A normal (inner) join drops sailors with no reservations. A LEFT OUTER JOIN keeps every row of the left table, filling the right side with NULL when there's no match. RIGHT and FULL outer joins work the same for the right side and both sides.

SELECT S.sid, S.sname, R.bid
FROM   Sailors S NATURAL LEFT OUTER JOIN Reserves R
WHERE  S.rating >= 9;

Changing data

INSERT INTO Sailors (sid, sname, rating, age)

Each statement is checked against keys, NOT NULL and foreign keys exactly as in the Relational model lesson. In UPDATE … SET x = (subquery), the subquery sees the table before the update.

Write: for each rating, the average age of sailors with that rating, only for ratings with at least 2 sailors.
SELECT S.rating, AVG(S.age) FROM Sailors S
GROUP BY S.rating HAVING COUNT(*) >= 2;
A Sailors table has ratings 5, NULL, 9. What do COUNT(*), COUNT(rating) and AVG(rating) return?
3, 2 and 7. Only COUNT(*) counts the NULL row; AVG is (5 + 9) / 2.
Is SELECT S.rating, S.age FROM Sailors S GROUP BY S.rating legal?
No. S.age is neither in GROUP BY nor inside an aggregate, and a rating group has several ages. Use MIN(S.age), AVG(S.age) etc., or add age to GROUP BY.

Q3 (25 points): relational algebra

Schema: Student(ID, Name, Department), ProjectTeam(TeamName, ID), Midterm(ID, Grade).

  1. Names of students in the team 'BEE'.
  2. IDs of students who have not been in any team yet.
  3. TeamNames of teams whose members are all from department 'CS'.
  4. Teams which include all students who got 100 in the midterm.
Show the answers

(i) Select the team, join to get names.

πName(σTeamName='BEE'(ProjectTeam) ⋈ Student)

(ii) “Not”: all students minus students in some team.

πID(Student) − πID(ProjectTeam)

(iii) “All members are CS” = “no member is outside CS”. Find teams with a non-CS member and subtract them.

πTeamName(ProjectTeam) − πTeamName(ProjectTeam ⋈ σDepartment≠'CS'(Student))

Q4 (25 points): bookstore queries

Schema: Book(isbn, title, publisher, price), Author(isbn, assn, aname), Customer(cid, cname, city, zipcode), Buy(tid, cid, isbn, year, month, day).

  1. Names of customers who live in Ankara and spent more than 500 TL in 2010.
  2. Pairs of customers who bought the same book.
  3. cids of customers who bought books from all publishers.
  4. cids of friends of Bob (cid 1234). Two people are friends if they bought more than 20 of the same books, meaning they share more than 20 ISBNs.

The paper doesn't say SQL or relational algebra. (i) and (iv) need sums and counts, which only SQL has, so the answers are in SQL. Each was run on small test data.

Show the answers

(i) Join the three tables, keep Ankara and 2010, then total per customer.

SELECT C.cname
FROM   Customer C, Buy Y, Book B
WHERE  C.cid = Y.cid AND Y.isbn = B.isbn
  AND  C.city = 'Ankara' AND Y.year = 2010
GROUP BY C.cid, C.cname
HAVING SUM(B.price) > 500;

(ii) Join Buy with itself on isbn. Y1.cid < Y2.cid removes a customer paired with themself and lists each pair once instead of twice.

SELECT DISTINCT Y1.cid, Y2.cid
FROM   Buy Y1, Buy Y2
WHERE  Y1.isbn = Y2.isbn
  AND  Y1.cid < Y2.cid;

(iii) Division pattern: all publishers minus the publishers this customer bought from must be empty.

SELECT C.cid
FROM   Customer C
WHERE  NOT EXISTS (
         SELECT B.publisher FROM Book B
         EXCEPT
         SELECT B2.publisher
         FROM   Buy Y, Book B2
         WHERE  Y.cid = C.cid AND Y.isbn = B2.isbn );

(iv) Pair each of Bob's purchases with someone else's purchase of the same book, then count shared books per person. DISTINCT matters if either bought a book twice.

SELECT Y2.cid
FROM   Buy Y1, Buy Y2
WHERE  Y1.cid = 1234
  AND  Y2.cid <> 1234
  AND  Y1.isbn = Y2.isbn
GROUP BY Y2.cid
HAVING COUNT(DISTINCT Y2.isbn) > 20;

Cheat sheet

Everything on one page for the last read before the exam.

Keys and foreign keys

  • Primary key: one per table, never NULL. UNIQUE: many allowed, NULL allowed.
  • Child insert/update pointing to a missing parent: rejected.
  • Parent delete/update still referenced: NO ACTION (default, reject), CASCADE, SET NULL, SET DEFAULT.
  • Parent insert and child delete never break a foreign key.
  • SET NULL on a column that's part of the child's primary key fails.

SQL

SELECT [DISTINCT] cols / aggregates
FROM     tables          -- 1 cross product
WHERE    row condition   -- 2 drop rows
GROUP BY cols            -- 3 make groups
HAVING   group condition -- 4 drop groups
ORDER BY cols [DESC]     -- 6 sort (SELECT is step 5)
  • SQL keeps duplicates; UNION / INTERSECT / EXCEPT remove them.
  • Non-aggregated SELECT columns must be in GROUP BY.
  • No aggregates in WHERE (use a subquery) and no nested aggregates.
  • SELECT name, MAX(age) FROM T without GROUP BY is illegal.
  • LIKE: _ one char, % any chars.
  • NULL: use IS NULL; WHERE keeps only true; COUNT(*) counts NULL rows, other aggregates skip NULLs.
  • “all” in SQL: NOT EXISTS (all things EXCEPT things this one has).
  • Highest: x >= ALL (…) or x = (SELECT MAX …).
  • Outer join keeps unmatched rows with NULLs.
